How it works

One ticket.
Four commands.

A session goes the way real work does. You pick up a ticket, dig into a codebase you have never seen, prove the fix holds and get a record of what you actually did.

  1. 01 · pgnd start

    Pick up a ticket

    You get a real repository with a bug report or feature request, in a fresh workspace. The tests that decide the outcome stay hidden.

  2. 02 · your editor

    Find it and fix it

    Read code you did not write, reproduce the problem and change it. Use your own editor and your own AI agent, or work without one.

  3. 03 · pgnd check

    Check as you go

    Run the checks in Docker whenever you like, as many times as you need. Red turns green only when the behaviour is actually right.

  4. 04 · pgnd submit

    Get verified outcomes

    Your work is frozen into a report you can trust: what passed, whether your test proves the fix and where your diff landed.

What you practise

The skills the job
actually asks for.

Puzzles train you to recall algorithms. Patchground trains the habits that matter on a team and in a practical interview, and gives you evidence to show for them.

Debugging unfamiliar code

Trace a symptom from a support ticket to its root cause in a codebase you have never opened.

Shipping a feature

Extend existing behaviour without breaking what already works, so the old tests stay green.

Proving the fix

Write a regression test that fails before your change and passes after. Patchground runs it on both versions to check.

Working with your AI

Direct Claude Code, Codex, a local model or no tool at all. Then use the outcomes to check what it really changed.

Keeping the change in scope

Fix the problem in the right place. The report shows exactly which files your diff touched.

Working to a timebox

Every challenge has a realistic timebox. See how long you really took and how many hints you used.

What you walk away with

Facts about your work,
not a score.

When you submit, Patchground freezes your workspace and computes a report from test runs alone. When it cannot prove something, it says so instead of guessing.

Why it exists

The interview changed.
The practice did not.

Live debugging, feature work in an unfamiliar repo, PR review, directing an AI tool under scrutiny. There was no free, structured way to rehearse any of it.

Local-first

No account, server or subscription. Image builds may use the network; checks run on an internal Docker network with resource limits.

AI optional, never required

Use Claude Code, Codex, a local model, or nothing—in your own editor. Patchground needs no API key and has no built-in AI; what your assistant sees is up to you.

Verified or it does not ship

Every published challenge must prove, in its container, that the broken state fails and a reference fix passes—deterministically.

Install

From install
to first ticket.

Patchground is an early, working release. Install it straight from GitHub: the curated challenges ship with the CLI, so there is nothing else to download. A PyPI package will follow.

  • ↳ Python 3.12+ and uv
  • ↳ Git and a running Docker engine (or Podman)
  • ↳ macOS or Linux; Windows through WSL2
First-session guide ↗README ↗
get started
uv tool install git+https://github.com/franndeli/patchground
pgnd doctor
pgnd list --builtin
pgnd start pagination-last-page

Then open the printed workspace in your editor and run pgnd check as you go. Finish with pgnd submit.

Publish your pack

Know a bug worth learning from?
Publish it. No pull request.

Your challenges live in your own repository. Patchground discovers it, re-runs its validator on every challenge, and lists what passes. The validator is the gate: nothing else is reviewed by hand, and nothing that fails is listed.

  1. 01

    Author and validate locally

    pgnd new my-bug scaffolds a runnable challenge; pgnd validate my-bug proves the broken state fails, the reference passes, and the result is stable. Fix every step until it reads valid.

  2. 02

    Make it a pack

    Put each challenge folder at the root of a public repository next to a pack.yaml that names it. Declare a content_license and provenance in every challenge.yaml; keep services: [].

    spec_version: "0.1"
name: my-pack            # lowercase, hyphens; first publisher keeps the name
version: 0.1.0
description: Bugs from a payments team
challenges: [my-bug]
  3. 03

    Tag the repository

    Add the GitHub topic patchground-pack to the repository. On other hosts, add your https:// clone URL to registry/sources.yaml. That is the whole submission.

  4. 04

    Appear

    Every few hours the registry clones tagged repositories, runs the policy checks and pgnd validate on each challenge in Patchground's CI, and publishes the result. Passing packs show up in the catalog with a verified badge; anything else is explained on the status page with the failing step.

Planned: pgnd pack publish to validate and tag in one command, and pgnd pack add <name> to install by name from this index. Until then the steps above are the whole process. The registry never lists hidden checks, hints or reference solutions; only the public metadata you see in the catalog. Authoring guide ↗
